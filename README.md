# tiny-tensor-compiler

A compact, correctness-first tensor compiler. The current milestone implements real end-to-end vertical slices rather than framework scaffolding:

```text
Python tensor expressions + typed external inputs
-> explicit typed tensor IR (concrete or bounded runtime symbolic/affine/linear dimensions)
-> verifier
-> optional runtime symbolic solving and concrete specialization
-> constant folding / algebraic simplification / dead-code elimination / canonicalization / CSE
-> explicit virtual-buffer CPU IR
-> liveness-based physical memory planning with read-only storage aliases
-> explicit loop/kernel IR with broadcast index maps, reshape copies, and root-relative view layouts
-> cost-ranked verifier-backed elementwise fusion
-> deterministic generated C11 source with conservative contiguous-loop linearization and vectorization hints
-> optional verified OpenMP native loop scheduling
-> process-local / optional persistent native shared-library cache
-> reusable compiled native executable handles
-> NumPy-backed scalar CPU interpretation/reference
```

The NumPy CPU executor remains the semantic baseline while lowering is made progressively more compiler-like through explicit buffers, memory planning, loop IR, generated C, and native execution. The native path compiles verified generated C into a shared library, reuses exact generated-source/compiler matches within the current process, optionally persists content-addressed artifacts across processes through `cache_dir=`, and invokes one stable output-first ABI through `ctypes` on POSIX-like GCC/Clang toolchains and Windows MSVC. Multiple returned tensors use ordered typed output pointers in that same entrypoint; single-output programs preserve the original one-`out` ABI. Native loop parallelism is an explicit opt-in (`parallel=True`), not an implicit change to the historical serial backend.

## Working example

```python
import numpy as np

from tiny_tensor_compiler import (
    GraphBuilder,
    compile_native,
    fuse_elementwise,
    lower_to_cpu,
    lower_to_loops,
    verify,
)

builder = GraphBuilder()
x = builder.input((3,), dtype="float32")
z = (x * 2 + 1).relu()
module = builder.finish(z)

verify(module)
loops = fuse_elementwise(lower_to_loops(lower_to_cpu(module)))
executable = compile_native(loops)
result = executable(
    inputs=[np.array([-2.0, 0.0, 3.0], dtype=np.float32)],
)
print(result)
```

`compile_native()` eagerly compiles or loads the native artifact and returns a reusable `NativeExecutable`. Repeated calls with new runtime input values reuse the same native code. The executable freezes the compiler command and cache identity chosen at compile time; if `clear_native_cache()` later releases process-owned serial shared libraries, the handle remains valid and safely reacquires or recompiles the same artifact on its next invocation. Single-output calls return one `numpy.ndarray`; multi-output calls return an ordered tuple and may receive an ordered sequence of preallocated output arrays. On Windows, OpenMP-enabled generated DLLs use a separate process-pinned lifetime because the worker runtime may retain generated code references beyond a parallel region; those pinned artifacts are intentionally not unloaded by `clear_native_cache()` and their marked staging directories are eligible for best-effort stale cleanup by a later process.

External inputs are explicit in tensor IR and numbered densely by declaration order:

```text
func @main() {
  %0 = input 0 : tensor<3xf32>
  %1 = const 2.0 : tensor<f32>
  %2 = mul %0, %1 : tensor<3xf32>
  %3 = const 1.0 : tensor<f32>
  %4 = add %2, %3 : tensor<3xf32>
  %5 = relu %4 : tensor<3xf32>
  return %5
}
```

Lowering preserves inputs as explicit write sources rather than turning caller data into constants:

```text
alloc b0 : tensor<3xf32>
b0 = input 0
alloc b1 : tensor<f32>
b1 = const 2.0
alloc b2 : tensor<3xf32>
b2 = mul b0, b1
alloc b3 : tensor<f32>
b3 = const 1.0
alloc b4 : tensor<3xf32>
b4 = add b2, b3
alloc b5 : tensor<3xf32>
b5 = relu b4
return b5
```

A separate deterministic memory planner maps owning virtual buffers onto physical slots while recording read-only aliases independently. Owning-slot reuse is allowed only after the previous root lifetime ends and only when the complete `TensorType` matches. Whole-storage views, positive-stride slices, signed-stride axis reversals, and axis permutations receive logical handles with `StorageLayout(offset, strides)` instead of new storage; every direct or transitive alias use extends the storage root lifetime. Returned values remain live through the terminal return block. The opt-in `borrow_inputs()` transform is applied only after planning and re-verifies its rewritten Loop IR, including alias handles.

The next lowering layer makes elementwise iteration and broadcasting explicit. For example, adding tensors with shapes `(2, 1)` and `(1, 3)` produces a `(2, 3)` loop whose reads are indexed as `lhs[i0, 0]` and `rhs[0, i1]`. Scalar broadcasts use an empty input index map, and ReLU uses identity indexing. CPU execution interprets these loop kernels one output index at a time rather than delegating broadcasting to vectorized NumPy operations. First-class `reshape` is a verified row-major copy into distinct storage. In contrast, `view`, positive-stride `slice`, signed-stride `reverse`, and compile-time `transpose` are explicit read-only aliases over one storage root; their logical shape and root-relative layout are carried separately and remain fusion boundaries.

The same verified loop IR can be emitted as deterministic C11 source. Owning physical buffers become fixed-width typed local arrays; logical views become typed pointer aliases plus verified root-relative layouts. Broadcast index maps and signed view strides become explicit row-major offset expressions, constants are embedded as typed literals, and external inputs become typed `const` pointers appended after the ordered output pointers. Non-scalar, non-empty kernels whose every input has the full output shape, identity indexing, and a contiguous logical layout are emitted as one contiguous `int64_t n` loop. Strided/permuted/reversed layouts use the general nested indexing path instead. Reshape copy kernels use one flat row-major `n` loop. In serial mode proven-independent flat loops receive the existing compiler-specific vectorization hint; the hint does not select a vector width or introduce parallel execution. Opting into `parallel=True` schedules verified non-scalar, non-empty general-C kernel iteration with `#pragma omp parallel for schedule(static)`: flat kernels parallelize `n`, broadcast/strided kernels parallelize only the outer `i0`, and verifier-safe non-scalar/non-empty partial `binary_into` effects parallelize their outer target axis. Every parallel region keeps its implicit barrier, so later kernels/effects observe the completed generation. Scalar and zero-extent kernels/effects remain serial. Explicit SSE2 kernels remain on their proven serial vector-loop + scalar-tail path and require exact contiguous `int32` layouts. Native returns from internal views gather logical elements into the existing contiguous caller-owned output ABI rather than exposing internal alias lifetimes.

Python scalar literals are coerced to the peer tensor's dtype (`float32_tensor * 2` remains `f32`). Tensor-vs-tensor operations use explicit `numpy.result_type` promotion.

External inputs remain exact and explicit. The ordinary `compile_module()` path requires fully concrete input shapes; runtime calls must match the declared input count, shape, and dtype with no silent cast. `compile_dynamic_module()` adds the bounded specialization boundary: named `SymbolicDim` values may appear directly, inside positive affine terms such as `2*B+1`, or inside positive multi-symbol linear expressions such as `2*B+W+3`. Multi-symbol axes contribute exact linear equations and the system must uniquely determine every unresolved symbol as a non-negative integer before Buffer/Loop/native lowering. Compile-time transpose simply moves already-typed dimensions between axes and adds no runtime shape equation; reverse leaves the logical shape unchanged and derives its signed physical layout only after the same concrete specialization boundary.

Copied input materialization remains the default compatibility behavior. Opting into `borrow_inputs()` or `compile_module(..., borrow_inputs=True)` / `compile_dynamic_module(..., borrow_inputs=True)` instead requires exact NumPy, C-contiguous, aligned arrays and binds verified external root slots directly; any input that would require a hidden normalization copy is rejected. Read-only view/slice/reverse/transpose handles may then alias that borrowed root without materialization. Writable roots remain compiler-owned: `binary_inplace` performs exact-typed add/mul over a fresh full root, while `binary_into` updates an injective partial alias region using an exact-typed RHS. If the public `binary_into` RHS aliases the destination root, it is first materialized through the existing reshape-copy snapshot path so later writes cannot contaminate reads. `copy_into` and `binary_into` keep `casting="exact"` by default; explicit `casting="widen"` accepts only `i32->i64`, `i32->f64`, and `f32->f64`, materializes the RHS to the destination dtype with existing typed arithmetic, and then emits the same exact-dtype effect. Narrowing, float-to-int conversion, and `i64->f64` remain rejected, as do inferred `-1` reshape dimensions, generic negative-step slice syntax, and runtime permutation axes.

Algebraic simplification is intentionally conservative: floating-point neutral-element rewrites are not enabled yet because preserving strict IEEE behavior, including signed zero and NaN edge cases, takes priority over reducing operation count.

Dead-code elimination is side-effect conservative. It removes only known-pure operations whose results have no uses; this includes read-only reshape/view/slice/reverse/transpose transforms, while `input` remains explicit so the declared runtime signature stays stable and `return` is never a candidate.

Canonicalization currently reorders only integer `add` and `mul` operands. Earlier SSA definitions sort first, which makes commutatively equivalent integer expressions structurally identical for later CSE without relying on object identity, hash iteration, or floating-point algebra assumptions. Floating-point operands are deliberately left untouched.

Common-subexpression elimination is deliberately exact rather than algebraic. It merges only currently supported exact expression keys; attribute-bearing slice/reverse/transpose operations are not given attribute-aware CSE in this phase.

Owning virtual buffers remain single-write. Physical root reuse is computed separately from logical alias handles. Every direct or transitive view use extends the owning root's lifetime; the planner therefore cannot recycle a root while an alias may still observe it. Alias layouts preserve dtype and are verified against both the minimum and maximum reachable backing-root offsets. Whole-storage views, positive-stride slices, signed-stride reversals, and axis permutations receive no independent physical allocation.

Loop IR remains conservative about writes. `LoopAlloc` values are storage roots; `LoopView` values are read-only logical handles with their own `TensorType` and root-relative `StorageLayout`. Ordinary kernels may not share an output storage root with any input. Destination-bearing effects are separate verified operations: `copy_into` writes a bounded alias region from an exact-dtype source that may broadcast exactly to the target; `binary_inplace` updates one fresh full compiler-owned root from a different-root exact-typed source; and `binary_into` performs exact-dtype broadcast add/mul through a fresh injective partial target alias, snapshotting same-root RHS values before either partial effect at the public builder boundary. Public widening is lowered before this layer, so Buffer/Loop write verification never sees mixed dtypes. Every root write advances a generation; stale view/root handles created against an older generation are rejected on later read or return. `parallel=True` may schedule a non-scalar/non-empty verified `binary_into` effect over its outer target axis because the target layout is injective and the RHS storage root is disjoint after any required snapshot; the implicit OpenMP barrier publishes the completed generation before following operations. `binary_inplace`, scalar effects, and zero-extent effects remain serial. Direct, affine, and relational symbolic dimensions are fully resolved before this layer.

Elementwise fusion remains explicit rather than automatic in `lower_to_loops()`. The planner builds dependency edges from adjacent binary kernels and refuses any candidate requiring reassociation or kernel reordering. Returned intermediates, storage aliases, and view creation remain observable boundaries. Reshape, view, slice, reverse, and transpose creation are not absorbed into or crossed by elementwise fusion in this phase.

Two- through four-node legal fused shapes retain historical checked chain/tree/chain-tree spellings. Five- and six-node legal binary windows use one structured `fused_dag` Loop kernel whose `FusedExpression` metadata contains the scalar semantics. Candidate ranking is a static structural heuristic, not benchmark evidence.

Generated-C scheduling remains deliberately conservative. Flat/SSE2 eligibility requires an actually contiguous logical layout in addition to the existing shape/index-map constraints. Non-contiguous positive-stride slices, negative-stride reversals, and ordinary axis permutations therefore use explicit general indexing from their verified `StorageLayout`; OpenMP may still schedule the outer loop of that general kernel. Verified `binary_into` effects reuse the same signed-stride write emitter and only add outer-axis OpenMP scheduling when `parallel=True`, so no competing write-index calculation is introduced. Internal aliases are zero-copy, while terminal native outputs remain contiguous caller-owned arrays populated in logical order.

Parallel mode is an opt-in scheduling policy over the same verified Loop IR. Each OpenMP kernel/effect retains its implicit barrier; no kernel reordering, `nowait`, asynchronous return, or graph-level task scheduling is introduced. Scalar/zero-extent kernels and effects remain serial, explicit SSE2 remains on its separate serial vector path, and full-root `binary_inplace` remains serial. This is an executable scheduling capability, not a speedup claim.

Native execution separates deterministic code generation, process-local loaded-artifact reuse, optional persistent storage, and reusable executable handles. Persistent artifact identity includes the generated source, compiler command/fingerprint, operating-system target, ABI shape, and concrete dynamic specialization. `clear_native_cache()` releases ordinary process-owned serial libraries and leaves user-owned persistent cache files intact.

Windows OpenMP execution keeps its stricter process-pinned lifetime boundary: generated OpenMP DLLs are not unloaded by `clear_native_cache()` because the runtime may retain outlined code references. PID-marked staging directories are only eligible for best-effort cleanup by a later process once the owner PID is no longer live.

A native C compiler is required to exercise `execute_native()`, `compile_native()`, or a newly observed `compile_dynamic_module()` specialization: a `cc`-compatible GCC/Clang toolchain on POSIX-like systems, or an MSVC developer environment exposing `cl` on Windows. ## Near-term compiler roadmap

The storage/mutation phase now includes dependence-aware OpenMP scheduling across independent effects, including conservatively proven disjoint regions that share one physical storage root. That promotion closes the immediate scheduler frontier: farming more alias/layout corner cases, tuning OpenMP knobs, raising fusion-node limits, or enumerating ad-hoc conversion pairs would be low-value.

The promoted compiler frontier is program-to-program differentiation. The bounded reverse-mode transform covers static scalar floating losses over `add`, `mul`, `sum`, `reshape`, whole-storage `view`, `transpose`, `reverse`, and positive-stride `slice`. Transpose/reverse adjoints stay zero-copy aliases; slice adjoints cross into the existing storage-generation/write-effect architecture through verified `copy_into`. A deterministic smooth-graph gradient-consistency campaign checks analytic transforms against central finite differences and shrinks reproducible divergences into canonical repro artifacts. Dynamic gradients cross the symbolic/runtime boundary by specializing the forward module before differentiation. `compile_adaptive_dynamic_gradient_module()` extends that path to multi-symbol runtime bindings and evaluates the existing compile-admission policy against each concrete gradient module: admitted bindings cache native execution while structural budget excess caches the verified Loop fallback, with one stable backend decision per binding. Mixed precision, unsupported write targets/operators, and non-scalar selected outputs for the scalar-gradient API still fail closed after specialization. Resource-managed dynamic-gradient facades now place native and adaptive gradient specializations under the same deterministic LRU ownership/release contract as ordinary dynamic execution, including truthful Loop-decision eviction and native artifact reacquisition. `vector_jacobian_product_module()` generalizes the static reverse-mode transform to arbitrary floating tensor outputs by appending an exact-type runtime cotangent input; composing it over first-gradient IR produces executable reverse-over-reverse Hessian-vector products without a separate higher-order backend. `differentiate_module()` keeps its scalar-output implicit-seed ABI. A bounded differentiated-effect contract covers `copy_into` when its writable target is a direct positive-stride slice of the current root: the root cotangent preserves untouched elements while zeroing the overwritten region, and the source cotangent gathers that region before ordinary unbroadcast. Reverse mode now records a generation-aware pre-write primal tape for backward-relevant values that alias the exact current root, so source/side computations may safely depend on pre-write root or slice values and ordered copy generations each retain their own primal snapshot. Tape materializations are forward-only compiler-owned values and are not themselves traversed as original differentiable operations. Non-direct copy targets remain fail-closed. Bounded arithmetic-write VJP semantics cover direct-slice `binary_into` and full-root `binary_inplace`. Partial `binary_into add` passes the output cotangent unchanged to the pre-write root and gathers the written region for the source; partial `mul` replaces the root cotangent's written region with `cotangent * source` and sends `cotangent * taped_prewrite_target` through ordinary unbroadcast to the source. Full-root `binary_inplace add` sends the entire cotangent to both root and source, while `mul` sends `cotangent * source` to the root and `cotangent * taped_prewrite_root` to the source. The same generation-aware primal tape also keeps source-side computations that depend on pre-write root values verifier-safe, so no write-effect-specific backend opcode or second tape path is introduced. With the current writable-effect family covered under bounded contracts, `compile_dynamic_vjp_module()` carries runtime-seeded VJPs across the symbolic boundary without letting the cotangent participate in symbol solving: original forward inputs determine the binding, the forward module is specialized first, and the resulting concrete VJP validates an appended cotangent against the exact specialized selected-output type while reusing the ordinary native specialization cache. `compile_adaptive_dynamic_vjp_module()` applies the same specialization ordering before the existing structural admission decision, so each concrete VJP deterministically caches either native execution or the verified Loop fallback under the established per-binding budget contract. Resource-managed dynamic VJP facades now place native and adaptive VJP specializations under the same deterministic LRU ownership/release lifecycle as ordinary and gradient dynamic execution, including final-owner native unload, external-handle reacquisition, and truthful Loop-decision eviction. `compile_dynamic_hvp_module()` carries bounded single-input Hessian-vector products across symbolic specialization by specializing the scalar-loss forward module first, constructing its concrete first gradient, applying a runtime-seeded VJP to that gradient, and treating the appended vector strictly as ABI data rather than a source of symbolic bindings. `compile_adaptive_dynamic_hvp_module()` now evaluates the existing structural admission policy on each concrete transformed HVP, caching one stable native-or-verified-Loop backend decision per symbolic binding while preserving the same single-`wrt` contract. Resource-managed dynamic HVP facades now place native and adaptive HVP specializations under the same deterministic LRU ownership/release lifecycle as ordinary, gradient, and VJP dynamic execution, including final-owner native unload, external-handle reacquisition, and truthful Loop-decision eviction. With reverse-mode, runtime-seeded VJP, dynamic/adaptive HVP, and their lifecycle parity closed under bounded contracts, `jacobian_vector_product_module()` provides a bounded source-to-source forward-mode transform over the proven pure floating subset. It preserves the original runtime inputs, appends exact-type tangent inputs for selected `wrt` inputs, and propagates tangent values through `add`, `mul`, `sum`, reshape/view aliases, transpose, reverse, and positive-stride slice using ordinary tensor IR across reference, CPU, Loop, and native execution; unsupported or non-direct write effects remain fail-closed. `compile_dynamic_jvp_module()` carries that transform across symbolic specialization: primal runtime inputs alone solve the complete binding, the forward module is specialized first, and one exact-type tangent per requested `wrt` input is appended only to the concrete JVP ABI while the resulting native executable is cached by the original binding. `compile_adaptive_dynamic_jvp_module()` applies the existing structural admission policy to each concrete JVP after specialization and tangent-ABI construction, caching one stable native-or-verified-Loop backend decision per original symbolic binding while preserving multi-`wrt` tangent ordering. Resource-managed dynamic JVP facades now place native and adaptive JVP specializations under the same deterministic LRU ownership/release lifecycle as ordinary, gradient, VJP, and HVP dynamic execution, including final-owner native unload, external-handle reacquisition, and truthful Loop-decision eviction. Forward-mode JVPs cross generation-advancing writes through ordinary verified tensor/write IR. For `copy_into`, the tangent path replays the write on an independent tangent root, preserving untouched tangent elements while replacing the written slice with the source tangent. Direct-slice `binary_into add` advances the tangent root with `target_tangent + source_tangent`; `binary_into mul` materializes the pre-write target primal before the primal generation advances, forms `target_tangent * source_primal + taped_target_primal * source_tangent`, and writes that replacement through verified `copy_into`. Full-root `binary_inplace add` produces `root_tangent + source_tangent`, while `binary_inplace mul` snapshots the pre-write root primal and produces `root_tangent * source_primal + taped_prewrite_root * source_tangent`; source tangents computed from pre-write root values remain valid because they are materialized before the primal generation advances. With the current writable-effect family covered under bounded forward-mode contracts, `run_jvp_consistency_campaign()` now supplies independent JVP correctness evidence on deterministic smooth tensor-output graphs. Each case compares the analytic JVP against a central directional finite difference and independently verifies JVP↔VJP dot-product duality; reproducible failures are shrunk across operation sequence, shape, primal inputs, tangent, and cotangent while retaining a canonical primal repro artifact. With forward/reverse transforms, dynamic execution, writable effects, lifecycle parity, and independent numerical/duality evidence all present under bounded contracts, `value_and_jacobian_vector_product_module()` provides a joint one-execution primal+JVP slice. `compile_pushforward_linearization()` and `compile_pullback_linearization()` provide symmetric reusable retained-state linearization for the bounded static floating subset, and `compile_linearization()` converges both directions onto one first-class retained state. The shared executable validates that pushforward and pullback derive the same deterministic primal/tape layout, executes that primal/tape once, freezes owned primal inputs plus only derivative-required intermediate primals, and returns one `LinearizationState` whose repeated `pushforward()` and `pullback()` queries reuse separate derivative executables without any path back to the primal executable. Direct-slice `copy_into`, direct-slice `binary_into add/mul`, and full-root `binary_inplace add/mul` now cross this lifetime boundary. Derivative-required aliases of the current root are materialized into compiler-owned tape tensors before a write advances storage generation; repeated pushforwards replay only tangent generations; repeated pullbacks reuse the same frozen snapshots. Additive writes preserve exact tangent/cotangent routing without extra multiplicative tape state, while multiplicative writes retain the exact pre-write target/root and source primals required by product rules. Caller-owned primal arrays may be mutated after `linearize()` without changing either derivative direction, and independent query counters make reuse observable without claiming performance. With the currently exposed writable-effect family closed under one retained-state lifetime protocol, `compile_dynamic_linearization()` carries that shared retained state across symbolic specialization: primal inputs alone solve each complete binding, the forward module is specialized first, one concrete `LinearizationExecutable` is cached per binding, and tangent/cotangent queries remain state-local ABI data rather than symbolic inputs. `compile_adaptive_dynamic_linearization()` evaluates the existing structural budget across the concrete retained-state bundle and selects one coherent backend for its primal tape, pushforward, and pullback components: all native when every component is admitted, otherwise all verified Loop. Each complete binding caches that stable bundle-level backend decision. Resource-managed dynamic and adaptive linearization facades now retain one logical LRU binding while accounting for the full native artifact set behind that retained bundle: primal tape, pushforward, and pullback identities are retained/released independently under the existing final-owner registry, adaptive Loop bundles own no native artifacts, and `released_native_artifact_count` counts actual artifact unloads rather than evicted bindings. With retained-state specialization, admission, and lifecycle parity closed, finite symbolic retained-linearization bundle sets package each binding as one compiler-free primal/tape + pushforward + pullback unit.
